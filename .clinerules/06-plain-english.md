# 06 — PLAIN ENGLISH, EVERY ANSWER, EVERY SESSION

The person I work with is **not technical**. Every answer must be understandable without
technical knowledge. This is a standing instruction from the project owner, given directly.

## How to write

- **Lead with the plain answer**, in one or two sentences, before any detail.
- **Never use a technical word without explaining it in the same sentence.** Example of the
  required style: "a server (a computer that stays switched on and answers requests from the app)".
- **Short sentences. Real names and real numbers** from this project. Never "some", "various",
  "etc." when the exact count is knowable.
- **Say what it means for the person**: what they must do, what it costs them in time or money,
  and what happens if they do nothing.
- **State limits plainly**: what is not known, not built, or needs someone else (a key, an
  approval, a business decision). Never bury a limit inside technical language, and never imply
  something works when it has not been checked.
- **One word per idea.** Define a term once, then keep using that same word.

## Precedence

This rule **OVERWRITES** any brevity, budget or token-saving guidance. Plain English is achieved
by deleting jargon and filler — **never** by deleting content, evidence, caveats or honesty.
Full reports stay full; the words just get simpler.

## Test before sending

Would a non-technical owner understand it on one read, and could they repeat the main point back
to someone else? If not, rewrite it.

## Applies to code comments too

The owner reads the code. Comments and status files in this project are written in the same plain
style, explaining *why* in ordinary words rather than restating *what* the line does.
